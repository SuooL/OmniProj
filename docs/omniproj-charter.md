# OmniProj — Git-Grounded Project Advancer for LLM-Era Research

> 把「你打算做什么」锚定到「git 实际发生了什么」,再用 agent 把想不清的推到可执行。
> Anchor intent to what git actually did — then let an agent push it to executable.

本文件是 OmniProj 的**产品宪法**:任何功能先过 §4(哲学)+ §6(non-goals);下游设计文档显式引用本文对应章节;宪法可修订,但修订直接替换正文、不留历史。

---

## §1. 问题

LLM 时代,多线程认知工作者的瓶颈从「执行能力」转到「维持推进」:

- **Re-entry 成本高**:回到一个搁置的课题,要 10–30 分钟翻 session、回忆判断、找卡点才能动手。
- **记录 ≠ 推进**:笔记 / PKM 擅长「记」,但记完常常**推不动**——想不清的条目躺着腐烂,计划与「实际做了什么(git)」分处两个宇宙,靠手动、会漂移的链接维系。
- **启动易、闭环难**:AI 让「开新坑」变便宜,「填到闭环」的成本没变 → 在研课题数 vs 实际推进数的 gap 越拉越大。
- **通用 agent 帮倒忙**:自主执行类 agent 要么替你跑(长程不可靠)、要么生成更多待消费的东西,不解决「我这堆课题下一步到底怎么推」。

## §2. 目标用户

**同时推进 3+ 个研究/开发课题、重度使用 LLM(Claude / Codex / ChatGPT)、产物以 git repo + LLM session 为主、自己有 taste 和判断习惯**的人。画像=研究者;可扩展到独立开发者、连续创业者、深度写作者。

**不服务**:想让 AI 全权替自己决定并执行的人;单项目工作者(Cursor / Claude Code 够用);团队协作(单用户)。

## §3. OmniProj 是什么(一句话 + 三层)

**OmniProj 是一个本地优先、git 为地基的科研推进器桌面 app:它把你的规划/任务/决策锚定到真实的 git 提交历史(planned vs. actual),主动提醒哪些课题在腐烂、卡在哪,并用 agent 把「想不清、推不动」的条目推到可执行——推荐由 agent 出,决策与执行由你拍。**

心智模型 = 三层 + 一个形态:

| 层 | 职责 |
|---|---|
| **记录 Record** | 两条时间线在 git flow graph 上对账:①*实际*=git 提交/分支图;②*意图*=**人主导**的富规划——task list(增删/状态/预期完成日期/问题备注/讨论)+ 计划/决策(含「决定不做」)。task↔commit 多对一。 |
| **推进 Advance** | 对条目提问、联网调研、完善需求、**拆解到可执行**;agent 可推荐,人采纳。LLM 真正出力处,也是核心痛点。 |
| **关注 Attend** | 每日主动提醒:哪些课题活跃、每个的任务清单、卡点堵点。受控 push。 |
| *形态 Form* | Tauri 桌面(原生通知/菜单栏),可视化优先、交互优先,LLM 嵌在恰当处。**形态服务上面三层,不自成目的。** |

**贯穿主线**:*把意图锚定到实际,再把意图推到可执行。*

## §4. 设计哲学(4 条)

### (a) 锚定意图到实际 —— 立身之本
计划、决策不能悬空。每条计划/决策尽量锚定到 git(commit / branch / 时间),形成 **planned vs. actual** 对账。**决定不做的**也要记(不必锚 git)——「废弃想法」对应 ADR 的 superseded 决策,不删只标。git 侧的锚定**尽量自动**(从 git 派生),手工维护的链接必然漂移。

### (b) agent 推进,人决策与执行 —— 唯一不可越的线
agent **可以**:回忆、提问、联网调研、完善需求、拆解任务、**推荐优先级与下一步**。agent **不可以**:未经你显式动作就自主执行(跑实验、改代码、提交)。可靠的是「人在环的推荐 + 拆解」,不可靠的是「长程自主执行」。**推荐权给 agent,拍板权与执行权留给人。**

### (c) 人主导规划与记录;工具只免除「重录 git 已知」的负担
项目推进的**设计由人主导**:建项目后做规划、增删任务、维护 task list、设预期完成日期、记问题备注、展开讨论——这是**核心活动**,工具要**支持好**(first-class,不是极简一行)。工具**不替你规划**;但也**不逼你手工重录 git 已经知道的**——提交、活动、腐坏度一律自动派生。

分界线:**人写「意图」(规划 / 任务 / 日期 / 备注 / 讨论),工具自动给「实际」(git),两者在 git flow graph 上对账。** 真正的反坟墓 = 人写的计划锚在 git graph 上、随真实提交对账,不漂成虚构;**不是**靠「少让人写」。仅应砍掉「新增需要你消费的二手产物」。

### (d) 受控主动 —— 该提醒时提醒,不该吵时闭嘴
系统**可以**主动提醒(「X 课题静默 N 天、next-action 还开着」),这是防止课题静默腐烂的关键。但主动性**受控**:push 的触发规则对用户可见、可调、可关;绝不视觉打断轰炸、绝不刷存在感。默认克制,阈值透明。

## §5. 核心原则

1. **状态即 markdown + git**:持久状态是 `~/.omniproj/` 下的人类可读 markdown;`~/.omniproj/` 本身是 git repo,每次写入=独立可回退 commit → 天然记录规划/理解如何演化,也是 planned-vs-actual 的历史基底。复制目录即迁移。
2. **非侵入 repo(硬约束)**:对原始 repo **零写、零改**——不写文件、不加 `.gitignore`/hook、不改配置,只**读**其 git。一切落 `~/.omniproj`,删掉即无痕。项目与 session 来源**显式注册**。
3. **作者身份不可混**:用户写的是 **ground truth**(`notes/`),agent 写的是 **derivative**(`auto/`)。agent 的推荐、拆解、调研结论一律先落 derivative;**只有用户显式采纳才升为 ground truth**。agent 永不覆盖用户内容。**即使允许推荐,这条不动**:agent 可以建议,不能替你落笔认账。
4. **git 锚点自动,否则不做**:planned-vs-actual 的「actual」侧必须自动从 git 拿;只能靠人手工维护的对齐宁可不做。
5. **受控 push 是显式旋钮**:提醒触发条件(静默天数、卡点…)是用户可见、可调、可关的 cadence,不是系统偷偷决定。
6. **人在环执行门**:任何改变外部世界的动作(跑命令、改文件、git 操作)必须由用户显式触发。agent 产出是**提案**,不是既成事实。
7. **本地优先**:持久状态全在本地;LLM API 可走远端,但输出落地必须本地;不上传状态。
8. **可读、可审计、可删**:agent 学到的偏好以 markdown 落 `~/.omniproj/`,随时能看、能改、能删。不存在用户看不到的隐式状态。

## §6. 明确不做(non-goals)

- **不做自主执行**:agent 不在没有你显式动作时跑实验、改代码、提交、发布(§4b、原则6)。推荐 ≠ 代劳。
- **不重造已解决的层**:
  - **通用 git 历史浏览器**——不跟 gitk / GitHub / lazygit 比谁的 commit 浏览做得好。**但** git flow graph 作为「task ↔ 提交」对账的画布(§3 记录层)**是我们的核心,不在此列**。
  - **通用 PKM / 笔记库**——不做「记」的竞品;我们做「记完能推进」。
- **不做通用 productivity / 日历 / 时间管理**:专为科研课题推进设计。
- **不做多用户协作 / 云同步**。
- **不做「可视化优先」的镀金**:形态服务三层。一个视图若不能先以「一屏排序列表」成立,就是过度设计。

## §7. 科学地基

映射到成熟且被验证的方法论:

- **ADR(Architecture Decision Records)**:append-only + superseding。这正是「记决策、含决定不做」的形式化——废弃想法=被 supersede 的 ADR,不删、只标。
- **需求可追溯性 / 端到端 traceability**(工作项⇄提交):planned-vs-actual 的工业标准。其警告:过度追溯会杀死实践——「追到能看见 gap 即止」→ 故原则4 坚持自动锚定。
- **Spec-driven development**(propose→implement→archive):意图与实现分离、可演化。
- **Human-in-the-loop agentic recovery**:grounded 迭代优于裸自主 → §4b 的依据。

## §8. 成功标准与反指标

**主指标**:重新进入一个搁置课题、从混沌到能动手的时间。基线 15–25 分钟 → 目标 < 5 分钟。**第二主指标**:被主动提醒后、真正推进(产生 commit 或采纳一个拆解)的课题比例。

**反指标(出现即失败信号)**:
- **明早不会为它开 app**:功能若通不过「明早我会为这个打开它吗」,它就该是个 markdown 文件,不是功能。
- **记录漂移成坟墓**:出现 `reconcile` / `sync` 类「手动对齐」需求 → 记录没做成 git 对账。
- **LLM 蔓延成聊天机器人**:真实工作还没想用两次,就在调「完善需求」的 prompt。
- **可视化镀金**:数据模型还没挣得图之前就先选图库。
- **推荐越界成代劳**:agent 未经采纳就写进 ground truth,或未经显式动作就执行。
- **推荐诱发依赖**:用户在**主线判断**上从「参考 agent」滑向「等 agent 拿主意」。允许推荐,但主线掌舵权是人的底线。

## §9. 定位 —— 哪一种「伟大」

**vim / tmux / git / Obsidian 谱系的 power tool**:行业内 serious user 近乎人手必备、十年级生命周期,不追消费级渗透。护城河 = **设计哲学 + 状态格式(markdown+git 可移植)+ provider 中立**,不是某个 feature。

**已知取舍(明知并接受)**:允许推荐 + 主动 push 有滑向「AI 替你决定」的风险;缓解 = §4b 人在环执行门 + §5 作者边界 + §8 反指标「推荐诱发依赖」。

## §10. 命名

**OmniProj** = **Omni**(全域、一眼看全)+ **Proj**(project / 项目)。它是 **Omni** 产品家族的一员(与 **OmniToken** 同源)。名字即定位:**Omni** = 一个入口纵览你所有在研项目的全貌(意图、实际、卡点尽收一屏);**Proj** = 把每一个项目推进到可执行。纵览全部,推进到底,方向盘始终在你手里。
